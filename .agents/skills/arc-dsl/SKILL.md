# ARC DSL Reference

ARC DSL is defined in `.ixx.arc` (module) or `.hxx.arc` (header) files. The CMake functions `target_generate_arc_modules()` and `target_generate_arc_headers()` automatically generate `.ixx` or `.hxx` files from these. For CMake setup see `/arc-cmake`. For node authoring see `/arc-nodes` and `/arc-node-builtins`.

## Generated Namespaces

Each DSL entity is placed in a specific namespace within the enclosing namespace:

| Entity | Generated namespace | Example |
|--|--|--|
| `trait` | `inline namespace trait` | `app::trait::Counter` (or just `app::Counter` since it's inline) |
| `cluster` | `namespace cluster` | `app::cluster::App` |
| `domain` | `namespace domain` | `shop::domain::ShopDomain` |
| `policy` | `namespace policy` | `app::policy::SecurityLevel` |

Traits are special: the `inline namespace trait` means `my::trait::TraitName` and `my::TraitName` are both valid and refer to the same type. This is because traits are the most commonly used entity in ARC. The `trait::` prefix can be included or omitted at the call site.

**Nodes** are not generated by DSL but by convention should be placed in `namespace node` (e.g. `app::node::Counter`). Alternatively, suffix the type name with `Node` (e.g. `CounterNode`) for clarity.

## Formatting

ARC DSL is whitespace-insensitive, but the following formatting conventions are recommended for readability and `grep`-ability:
- 4-space indentation (note: top-level namespaces do not add indentation, but get an extra blank line after the opening brace and before the closing brace)
- End braces always on their own line, commenting after closed namespaces (e.g. `} // namespace my::ns`)
- Blank lines between entities (traits, clusters, domains, policies)

## Traits (.ixx.arc)

Traits define interfaces between nodes.

```arc
export module <project>.traits;

namespace <project> {

trait <Name>
{
    // Method with return type
    method(int a, int b) -> int

    // Const method, return type deduced (decltype(auto))
    query() const

    // Void method
    doSomething()

    // Variadic template method (accepts any arguments)
    log(...)

    // Precondition: validated before call
    divide(int a, int b) -> int
        pre (b != 0)

    // Postcondition: binding name is optional
    count() const -> int
        post (r: r >= 0)   // r binds to return value
    abs(int x) -> int
        post (self.query() >= 0) // no binding name, return value not referenced

    // Template method (not enforced by ARC until called)
    template<class T> process(T value)

    // Constrained template method
    template<std::size_t I, class T>
    complex(T t, auto a) -> std::same_as<double> auto

    // Default implementation: used when a node does not define its own.
    // `self` is a trait view, so `self.x()` dispatches through the trait
    // (spies/overrides apply). Const methods get a `const&` self.
    reset() {}
    summary() const -> int { self.reset(); return 0; }
}

} // namespace <project>
```

Non-template, non-defaulted methods are added to the `arc::Implements` concept and enforced at `getNode`/`asTrait` time. Template methods are only checked when actually called.

**Contracts** — use `pre`/`post` selectively where a method has genuinely invalid inputs or meaningful invariants. They also serve as documentation of intent.

### Associated Types

Traits can require types from implementors or from the graph root:

```arc
// Require types from implementor (resolved via arc::ResolveTypes)
trait Storage [Types]
{
    type GetResult
    type Children

    get(std::string_view path) const -> Types::GetResult
}

// Require types from graph root (resolved via Context::Root)
trait Configurable [Root]
{
    root Config

    configure(Root::Config const& cfg)
}

// Both, with aliases
trait Complex [T = Types, R = Root]
{
    type Token
    root PassHash

    // Can add concept constraints
    requires std::integral<typename T::Token>

    // Constrain mutable/const implementations
    requires (std::string s) { impl_.mutableMethod(s) }
    requires const_.constMethod(0)
}
```

### Trait Aliases and Composition

```arc
trait AltName = BaseTrait         // Alias (disambiguation)
trait Combined = Trait1 + Trait2  // Composition (implements both)
```

A node implementing `Combined` also implicitly implements `Trait1` and `Trait2` individually.

### Qualified Namespace

Traits can be defined with an inline namespace instead of a wrapping block:
```arc
trait my::app::MyTrait { ... }
// Generates: my::app::inline trait::MyTrait
```

## Protocols (.ixx.arc)

Protocols live inside `namespace protocol` — `protocol Connection` inside `namespace app` produces `app::protocol::Connection`.

```arc
namespace app {

protocol Connection {
    Closed <-> Open -> Error -> Dead         // top-level group: arc::States<Connection>::Main
    Closed <-- Error

    per(std::string name) {
        state Channel {                      // per-key group: arc::States<Connection>::Channel
            Disconnected --> Connecting --> Connected
            Disconnected <-- Connecting | Connected
            Connected implies Open           // invariant: if Connected then Open (one-way)
        }
        state Encryption {
            Plain --> Secured
            Secured iff Connected(name)      // invariant: Secured iff Connected (two-way)
        }
    }

    hasPendingData(std::string name) implies Connected(name)  // predicate: true only valid when Connected
    isDead iff Dead                                           // predicate: must exactly mirror Dead
}

trait Network [Protocol = protocol::Connection] {
    open() -> bool
        is Closed then (success: success == proto.Open())
    connect(std::string name) -> bool
        is Open
        if (proto.Disconnected(name)) then (success: success ? proto.Connecting(name) : proto.Disconnected(name))
        if (proto.Connecting(name))  then (success: success ? proto.Connected(name)  : proto.Disconnected(name))
    close() -> bool
        is Open then (success: success == proto.Closed())
    kill() -> void   is Error then Dead
    reset() -> bool  to Closed
    read(std::string name) -> std::string
        is hasPendingData(name)   // no exit clause → state must not change
}

} // namespace app
```

**Arrows:** `A --> B` (A→B), `A <-- B` (B→A), `A <-> B` (both). Chain: `A --> B --> C`. Sets: `A | B --> C`.
First state mentioned = default. All states must be reachable from it (generator enforces).

**Invariant/predicate targets:** bare name `Open` → `proto.Open()`, parameterised `Connected(name)` → `proto.Connected(name)`, or `(cpp_expr)`.

| Form | Check |
|--|--|
| `V implies Expr` | `!V \|\| Expr` — if variant active, target must hold |
| `V iff Expr` | `V == Expr` — variant active exactly when target holds |
| `name implies Expr` | predicate: `!ret \|\| Expr` checked after every call |
| `name(T p) iff Expr` | predicate: `ret == Expr` checked after every call |

**Contract clauses** (bare names or `(proto.X())` expressions):

| Clause | Entry | Exit |
|--|--|--|
| `to State` | — | post-state = State |
| `is Pre` | Pre holds | — |
| `is Pre then Post` | Pre holds | Post holds |
| `is Pre then (r: expr)` | Pre holds | expr holds (r = return value) |
| `if Cond then (r: expr)` | — | if Cond held on entry, expr holds |

Every state change must be a declared transition. A method with no exit clause (`then`/`to`/`if…then`) must not change state.

**Implementing:** list both trait and protocol in `arc::NodeImpl`. State accessors are `const`; trait methods are mutable. Group `G` generates accessor `protoG(args...)` → `States::G` and variant query `Variant(args...)` → `bool`.

```cpp
struct Network : arc::NodeImpl<trait::Network, protocol::Connection>
{
    using Main   = arc::States<protocol::Connection>::Main;
    using Channel = arc::States<protocol::Connection>::Channel;

    Main    protoMain() const { return state; }
    Channel protoChannel(std::string const& name) const { ... }
    bool    hasPendingData(std::string const& name) const { ... }
    bool    isDead() const { return state == Main::Dead; }

    bool open()  { state = Main::Open;   return true; }
    bool close() { state = Main::Closed; return true; }
    // ...
};
```

## Clusters (.ixx.arc)

Clusters wire nodes together, resolving all dependencies at compile time. The generated type is placed in `namespace cluster`.

```arc
export module <project>.clusters;

import <project>.node.foo;
import <project>.node.bar;
import <project>.traits;

namespace <project> {

cluster <Name>
{
    // 1. Node definitions
    foo = node::Foo
    bar = node::Bar
    logger = node::Logger

    // 2. (Optional) enable global node access for all nodes
    [[@global]] @all ==> @global

    // 3. Sink connections (must come before normal connections)
    // Connects all siblings + parent to logger
    [Logger] @all --> logger
    // Shorthand (omitting arrow): [Logger] logger

    // 4. Normal connections
    [Something]
    foo --> bar // foo depends on bar

    [Foo <-> Bar]
    foo <-> bar // Bidirectional: foo gets Bar from bar, bar gets Foo from foo

    [Logger]
    foo, bar --> logger      // Multiple sources

    // 5. Trait aliases (for brevity)
    using A = trait::Apple, B = trait::Banana

    // 6. Expose trait to @parent (for nested clusters)
    [Trait] .. --> foo

    // 7. Resolve dependency in parent
    [External] bar --> .. // bar gets External from @parent
}

}
```

### Connection Arrows

| Arrow | Meaning |
|--|--|
| `a --> b` | `a` depends on `b` for the bracketed trait |
| `a <-- b` | `b` depends on `a` |
| `a <-> b` | Bidirectional (requires `[TraitA <-> TraitB]` header) |

### Special Markers

| Keyword | Shorthand | Meaning |
|--|--|--|
| `@parent` | `..` | Parent cluster |
| `@global` | `^` | Global node |
| `@all` | `*` | All sibling nodes and the parent (sink connections only) |
| `@notrait` | `~` | No-trait connection |

### Trait Disambiguation (Renaming)

When two nodes implement the same trait and a dependent needs to distinguish them:
```arc
[trait::Cherry]
apple (trait::SourCherry) --> sourCherry
// apple.getNode(trait::sourCherry) resolves to sourCherry.asTrait(trait::cherry)
```

### Daisy-Chain Connections

Chain multiple nodes in sequence:
```arc
[trait::Pipeline]
@parent --> nodeA --> nodeB --> nodeC
// parent depends on nodeA, nodeA depends on nodeB, nodeB depends on nodeC
```

### Fan-Out (One-to-Many)

**Explicit** — creates an intermediate `arc::Repeater` node:
```arc
[trait::Notify]
manager --> {listenerA, listenerB, listenerC}
```

**Implicit** — same source repeated across lines (equivalent semantics):
```arc
[trait::Notify]
manager --> listenerA
manager --> listenerB
manager --> listenerC
```
All targets of a repeated trait from the same source must be in a single connection block.

### No-Trait Connections

Use `@notrait` (or `~`) for traitless, type-safe connections. The client gains access to all public members of the provider:
```arc
[@notrait] client --> provider
// Shorthand for: [arc::NoTrait<Provider>] client --> provider
// Client accesses via: getNode<Provider>()->doWork()
```

Multiple no-trait sinks in one line: `[@notrait] logger, metrics`

Cannot mix no-trait and named trait connections for the same target.

### Templated Node Definitions (Wrapper Syntax)

Higher-order nodes can be applied with `:` syntax for readability:
```arc
cluster MyCluster
{
    // Read left to right: Node1 wrapped in InGroup
    topSecret = node::Node1 : arc::InGroup<policy::Classification::TopSecret>
    // Equivalent to: arc::InGroup<node::Node1, policy::Classification::TopSecret>

    onThread0 = node::Node2 : arc::OnThread<0>
    // Equivalent to: arc::OnThread<node::Node2, 0>

    // Multiple wrappers chain left to right
    collected = node::Node3 : arc::AnyThread : arc::Collection<int>
    // Equivalent to: arc::Collection<arc::AnyThread<node::Node3>, int>
}
```

### Nested Clusters and Inter-Cluster Wiring

Subclusters communicate through the parent. There are three connection scopes:

```arc
cluster FooBar
{
    foo = node::Foo
    bar = node::Bar

    [Bar]  foo --> bar       // 1. Internal: foo depends on bar for Bar
    [Foo]  .. --> foo        // 2. Expose: parent cluster (Outer) resolves Foo to foo
}

cluster Baz
{
    baz = node::Baz

    [Foo]  baz --> ..        // 2. Consume: baz resolves Foo to parent cluster (Outer)
}

cluster Outer
{
    fooBar     = cluster::FooBar
    bazCluster = cluster::Baz

    [Foo]  baz --> fooBar    // 3. Inter-cluster: Outer routes bazCluster.baz Foo dependency to fooBar.foo
}
```

**Note:** Connection blocks use local subcluster names only — no dot-paths (`fooBar.foo` is NOT valid in `.ixx.arc`).

### Trunk Connections (Inter-Cluster Bulk Wiring)

Named after **network trunking** — a single high-capacity link that carries many separate channels between two endpoints. Trunks bundle multiple traits into one connection line.

#### Cluster Trunks

A cluster declares a curated **trunk** — a named subset of its exposed traits — which a sibling node or subcluster can depend on over one connection line:

```arc
cluster Producer [Trunk = A + B + C]   // subset; D exposed but not in trunk
{
    // ...

    [A] .. --> a
    [B] .. --> b
    [C] .. --> c
    [D] .. --> d
}

cluster Consumer
{
    // ...

    [A] x --> ..
    [B] y --> ..
    [C] z --> ..
}

cluster Outer
{
    producer = cluster::Producer
    consumer = cluster::Consumer
    node = node::Node

    [[cluster::Producer]]
    consumer ==> producer    // consumer gets A + B + C
    [D]
    node     --> producer    // D available as normal
}
```

### Inline Trunking

You can also define a trunk inline without a cluster declaration.

```arc
cluster MyCluster
{
    abc = node::ABC
    xyz = node::XYZ

    [[A + B + C]]
    xyz ==> abc
}
```

#### Bi-directional Trunks

When two clusters depend on each others' trunks, declare it in one block with `<=>` separating the two trunks. Connections inside may use `==>`, `<==`, or `<=>` per pair — analogous to `[A <-> B]` for traits.

```arc
cluster Outer
{
    data    = cluster::Data
    compute = cluster::Compute
    repl    = node::Repl

    [[cluster::Data <=> cluster::Compute]]
    data    <=> compute   // mutual: data gets Compute trunk, compute gets Data trunk
    repl    ==> compute   // repl gets Compute trunk from compute
    data    <== repl      // repl get Data trunk from data
}
```

Equivalent to two single-direction blocks:
```arc
[[cluster::Data]]    repl, compute ==> data
[[cluster::Compute]] repl, data    ==> compute
```

Both sides of `<=>` must be single cluster trunks — inline trunks with `+` cannot be bi-directional.

**Rules:**
- Trunk traits in `[Trunk = ...]` must each have a matching `[T] .. --> node` exposure (generator-checked).
- Trunk consumption: double brackets `[[...]]` + `==`-style arrow (`==>`, `<==`, `<=>`). Mixing `-` and `=` arrow forms is rejected.
- `[[...]]` can contain a single cluster (cluster trunk), multiple traits joined with `+` (inline trunk), or two cluster trunks joined with `<=>` (bi-trunk).
- `<=>` is only allowed inside a bi-trunk block — in a uni-trunk block both directions would carry the same trunk, so it is rejected.
- The bi-trunk separator must be `=`-style (`<=>`); `<-->` is rejected.
- Inline trunks with `+` cannot use `<=>` — each side of a bi-trunk must be a single cluster trunk.
- No sinks, no `@notrait` in trunk blocks.

**Use when:** a subcluster has a coherent public face and a consumer needs most of it, or you want to bundle traits inline. Use the bi-trunk form when the mutual coupling between two clusters is the headline fact.

### Parameterised Clusters

```arc
cluster MyCluster [Root]
{
    storage = Root::StorageImpl  // Type injected from graph root
}

// With aliases for Context and Root:
cluster MyCluster [C = Context, R = Root]
{
    node = R::NodeType
}
```

## Domains (.ixx.arc)

Domains are strict clusters for large systems that encourage scale-free graph topologies. The generated type is placed in `namespace domain`.

Key differences from clusters:
- Single **nexus** node (first node listed) that coordinates the domain
- Only the nexus connects to `@parent`
- Naming rules enforced at compile time:
  - `pascalCase` — stateless unary node
  - `CamelCase` — stateful unary node
  - `ALL_CAPS` — sub-cluster or sub-domain
- Unary-to-unary connections must use strong arrows `--->>>` (get uglier as count increases, discouraging coupling)
- Sub-clusters/sub-domains may connect directly to each other
- Unary sub-nodes may NOT connect to non-unary nodes (except their own nexus)
- All sub-nodes must have `arc::Depends`/`arc::Uses` specified (even if empty)
- Sink traits not allowed (except to `@global`)

```arc
namespace shop {

domain ShopDomain
{
    Api = node::ShopRestAPI         // First node = nexus (stateful has uppercase name)
    CUSTOMER = domain::CustomerDomain
    ORDER = domain::OrderDomain

    using req = trait::ShopRequest, res = trait::ShopResponse

    [res <-> req]
    @parent <-> Api

    [trait::OrderCancel]
    Api, CUSTOMER --> ORDER
}

} // namespace shop
```

## Policies (.ixx.arc)

Policies enforce compile-time access control between node groups. The generated type is placed in `namespace policy`.

```arc
policy SecurityLevel
{
    // Groups are created implicitly when first named in a connection.
    // Only aliases (Name = ExternalType) need explicit declaration.

    // Arrow types:
    Untrusted -> Trusted       // Untrusted can read Trusted
    Trusted => Privileged      // Trusted can read-write Privileged
    Untrusted <-> Trusted      // Bidirectional read
    Trusted <=> Privileged     // Bidirectional read-write
    MID <-|=> HIGH             // MID can read-write HIGH, HIGH can read MID
    MID <=|-> HIGH             // MID can read HIGH, HIGH can read-write MID

    // Chaining: read up, write down
    Untrusted -> Trusted -> Privileged
    Privileged => Trusted => Untrusted
}
```

**Arrow summary:**

| Arrow | Meaning | Equivalent | Decomposition |
|--|--|--|--|
| `A -> B` | A can read B | `B <- A` | |
| `A => B` | A can read-write B | `B <= A` | |
| `A <-> B` | Bidirectional read | `B <-> A` | `A -> B` + `A <- B` |
| `A <=> B` | Bidirectional read-write | `B <=> A` | `A => B` + `A <= B` |
| `A <-\|=> B` | A read-writes B, B reads A | `B <=\|-> A` | `A => B` + `A <- B` |
| `A <=\|-> B` | A reads B, B read-writes A | `B <-\|=> A` | `A -> B` + `A <= B` |

No write-only access exists — write (`=>`) always includes read.

**Apply to nodes:**
```arc
myNode = node::MyNode : arc::InGroup<policy::SecurityLevel::Privileged>
```

**Special group names:**

| Name | Shorthand | Meaning |
|--|--|--|
| `@nogroup` | `~` | Unclassified nodes only (nodes in no explicit group) |
| `@any` | `*` | Node in any consenting group (unclassified nodes consent by default) |

Mutual consent still applies — `@any` is not a unilateral bypass. Same-group connections are always permitted separately and are unaffected.

`@nogroup` scopes the same open-to-all behaviour to unclassified nodes only.

Note: `*` means `@any` in policy context; in cluster connection blocks it means `@all` (all sibling nodes). The two uses are unambiguous by position.

**Key rules:**
- Same-group connections are always permitted (with write access)
- Different-group connections require explicit arrows in **both** policies (see external group linking below)
- Connections are **NOT transitive**: `A -> B` and `B -> C` does NOT imply `A -> C`
- Nodes without a group use the default group (`@nogroup` or `~`); unclassified nodes defer to whatever the other group's policy says — if the other group explicitly permits the connection, it is allowed

**Multiple group membership:**
```arc
node = Node : arc::InGroup<policy::Access::User, policy::Access::Admin>
```
- Reading: need permission to read from **any one** group (OR)
- Writing: need permission to write to **all** groups (AND)

**Group aliases** — reference groups from other policies:
```arc
policy CombinedPolicy
{
    External = SecurityLevel::Untrusted  // Alias (explicit declaration required)

    External => Public   // External gains read-write access to Public; Public auto-created
    Public -> External   // Public declares it can read External
}
```

**External group linking (mutual consent):**

A policy can declare a connection where one or both sides are external (aliased) groups. However, the connection is only active when **both** policies declare it — each side must explicitly permit the link.

```arc
// In policy SecurityLevel:
policy SecurityLevel
{
    Internal = Compartment::Internal  // alias (explicit); Untrusted/Trusted auto-created below

    Trusted -> Internal   // Trusted declares it wants to read Internal
}

// In policy Compartment:
policy Compartment
{
    Edge = SecurityLevel::Trusted     // alias (explicit); Internal auto-created below

    Edge -> Internal                  // Internal permits Edge (Trusted) to read it
}
```

Both declarations are required — the connection is blocked if either policy omits its side. This means two independent policies can jointly agree to permit a cross-policy link without either policy being able to unilaterally open access.

**Cluster inheritance** — clusters inherit the group classification applied at the parent level:
```arc
cluster MainSystem
{
    critical = cluster::CriticalSubsystem : arc::InGroup<policy::Safety::ASIL_D>
    // All nodes inside CriticalSubsystem inherit ASIL_D
}
```
